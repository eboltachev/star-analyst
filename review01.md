# Техническое ревью MVP (по требованиям заказчика)

Дата: 2026-03-21  
Объект ревью: текущий PR `feat: compact OSINT verification MVP — FastAPI monolith, worker, adapters, AI stubs, UI, tests`.

## 1) Executive summary

Текущая реализация **частично соответствует** целевому MVP: правильно выбран стек (монолит + worker + PostgreSQL/pgvector + SSR UI), есть базовый сквозной сценарий и задел под расширение.  
Однако в текущем виде решение **не проходит по ряду обязательных требований** заказчика для «полноценного MVP»:

- pipeline фактически запускается синхронно в веб-запросе, а не как фоновая задача через worker;
- интеграции источников и AI-провайдеров сделаны как локальные фикстуры/заглушки и не используют заявленный http/OpenAI-compatible transport в runtime;
- explainability/traceability реализованы неполно (нет строгой привязки ключевых утверждений отчёта к evidence с формальным mapping);
- чат не реализует полноценно RAG по сохранённым данным (нет retrieval/ranking/цитирования с provenance в ответе);
- E2E Playwright — smoke-заглушка, не покрывает требуемый пользовательский сценарий;
- часть нефункциональных требований (structured logging по операциям, retries/rate limit/httpx в адаптерах, корректная оркестрация статусов, legal-safe поведение при недоступности источников) покрыта недостаточно.

Ниже — детализированный разбор и предложения по исправлению с приоритетами.

## 2) Матрица соответствия требованиям

Оценки:
- ✅ выполнено
- ⚠️ частично
- ❌ не выполнено / критичный разрыв

### 2.1 Архитектура и инфраструктура

1. Один Python-репозиторий, backend-монолит, worker, PostgreSQL, pgvector, local storage, docker compose  
**Статус:** ⚠️  
**Комментарий:** структура соответствует, есть Dockerfile/compose, миграция с `vector`. Но runtime default DB — SQLite, что может расходиться с обязательным PostgreSQL для основной конфигурации. Для dev/test допустимо, но в MVP-doc лучше жёстко разделить profile/ENV.

2. Готовые `docker-compose.yml`, `.env.example`, `README.md`, миграции, тесты  
**Статус:** ✅

3. Без overengineering (Kafka/Celery/Neo4j/ES и т.п.)  
**Статус:** ✅

### 2.2 Функциональные требования

1. Форма нового запроса (ФИО/дата/ИНН/комментарий/источники/файлы)  
**Статус:** ✅

2. Источники из конфигурации + дефолтные 3 источника  
**Статус:** ✅

3. Обработка вложений (OCR + извлечение сущностей/признаков + отображение пользователю)  
**Статус:** ⚠️  
**Комментарий:** извлечение есть как stub regex и не использует multimodal API в runtime; извлечённые данные не показаны пользователю как отдельный UI-блок (промежуточный результат).

4. Экран мониторинга с near real-time статусами (SSE/WebSocket)  
**Статус:** ⚠️  
**Комментарий:** SSE есть, но пайплайн выполняется синхронно в `POST /requests`, из-за чего мониторинг теряет смысл как «live progress» и пользователь ждёт завершения до редиректа/показа.

5. Адаптеры источников (единый интерфейс, httpx, timeout/retries/rate limit, логирование, нормализация)  
**Статус:** ❌  
**Комментарий:** интерфейс/нормализация есть; но фактический search читает локальные json-фикстуры, `httpx`/retry/rate-limit/технический журнал запросов-ответов не реализованы как runtime-path.

6. Нормализованная модель данных (перечень сущностей)  
**Статус:** ✅

7. Аналитическая справка с требуемой структурой + explainable mapping к evidence  
**Статус:** ⚠️  
**Комментарий:** отчёт есть, но структура неполная (нет полноценных секций: таймлайн, ограничения/неопределённости в требуемой детализации, per-source breakdown), и нет формальной привязки каждого ключевого тезиса к evidence IDs.

8. Интерактивный граф связей + связь с текстовыми выводами и доказательствами  
**Статус:** ⚠️  
**Комментарий:** Cytoscape есть, но отсутствует полноценная детализация по клику (всплывающая панель с evidence/provenance), и привязка к конкретным фрагментам отчёта ограничена.

9. Чат по сформированной справке (RAG локально, evidence-citations, no hallucination, честный отказ)  
**Статус:** ⚠️  
**Комментарий:** чат работает на простом context list без retrieval/ranking, без строгих ссылок на provenance и без систематического контроля «доказуемости» ответа.

10. Дозапуск выбранных адаптеров из чата  
**Статус:** ❌

11. История запросов + фильтрация + поиск  
**Статус:** ✅

12. Аутентификация (локальные пользователи, cookie session)  
**Статус:** ✅

### 2.3 Тестирование

1. Unit: нормализация адаптеров, entity extraction, evidence, graph, retrieval  
**Статус:** ⚠️  
**Комментарий:** базовые unit есть, но retrieval-layer как отдельный компонент не выделен/не протестирован глубоко.

2. Integration: request->pipeline->sources->report->db  
**Статус:** ⚠️  
**Комментарий:** есть один основной тест, недостаточно негативных сценариев (source down, timeout, partial failure).

3. E2E Playwright: полный user-flow  
**Статус:** ❌  
**Комментарий:** текущий e2e — smoke-проверка наличия пакета, не покрывает UX-флоу.

4. Тесты оффлайн, без реальных сайтов/моделей  
**Статус:** ✅

## 3) Критичные замечания (P0)

### P0-1. Неверная оркестрация: pipeline выполняется в HTTP запросе
**Риск:** зависание UI, плохой UX, нет реального мониторинга, деградация под нагрузкой.  
**Что исправить:**
- в `POST /requests` только создавать request/job и событие `created`; возвращать редирект немедленно;
- worker должен быть **единственным исполнителем** pipeline;
- в БД добавить/использовать явную очередь задач (`jobs` или статус/lock поля в `requests`) с атомарным claim (например, `FOR UPDATE SKIP LOCKED` для PostgreSQL).

### P0-2. Адаптеры источников не реализуют требуемый runtime-контур
**Риск:** функционал «по открытым источникам» фактически отсутствует; несоответствие ТЗ.  
**Что исправить:**
- оставить fixture mode для тестов, но добавить production-path через `httpx`;
- внедрить timeout/retry/backoff/rate-limit на адаптер;
- логировать request/response метаданные в техжурнал без PII утечек;
- корректно обрабатывать недоступность/ручное подтверждение и отражать это в status/report.

### P0-3. E2E тесты не покрывают обязательный сценарий
**Риск:** заявленные требования QA не подтверждены.  
**Что исправить:**
- написать полноценный Playwright e2e: login → form → source select → file upload → monitor updates → report → graph visible → chat answer;
- запуск в CI с локальными моками и предсказуемым seed.

### P0-4. Чат не обеспечивает требуемую explainability / anti-hallucination дисциплину
**Риск:** недостоверные ответы без доказательств.  
**Что исправить:**
- выделить retrieval слой (chunking + scoring + top-k);
- добавлять в ответ обязательные цитаты `evidence_id`, `source_id`, `url/record_id`;
- внедрить policy: при недостатке контекста — формализованный отказ + предложение дозапуска источника.

## 4) Важные замечания (P1)

1. **Отчёт не соответствует полной структуре ТЗ** (перечень источников, таймлайн, ограничения и неопределённости, per-source секции и обоснования выводов с evidence map).  
2. **Нет UI показа промежуточного extraction результата** (извлечённые сущности из вложений до/во время поиска).  
3. **Graph UX**: по клику нет полноценной карточки узла/ребра с evidence/provenance и ссылкой на фрагмент отчёта.  
4. **Конфигурация и окружения**: требуется явное разделение DEV/TEST/PROD defaults (PostgreSQL как primary).  
5. **Security hardening MVP**: cookie flags (`HttpOnly`, `Secure`, `SameSite`), CSRF для форм (минимум double-submit token), ограничение upload size/content-type whitelist.

---

## 5) Замечания средней важности (P2)

1. Structured logging есть, но лучше стандартизировать поля (`request_id`, `source_id`, `step`, `duration_ms`, `error_code`).  
2. В миграции и ORM стоит унифицировать enum типы (чтобы избежать дрейфа между SQLite fallback и PostgreSQL).  
3. Нужен explicit data retention policy для uploaded files и extracted artifacts.  
4. История: желательно добавить пагинацию и сортировку для больших объёмов.

---

## 6) Рекомендуемый план доработок (минимум для принятия MVP)

### Этап A (обязательный, 1–2 итерации)
1. Перенести выполнение pipeline в worker-only модель с очередью задач и корректным lock/claim.  
2. Добавить runtime-путь адаптеров на `httpx` + retries + rate limit + error mapping, fixture mode оставить только для тестов.  
3. Доработать report generator до структуры из ТЗ с явной `claim -> evidence[]` таблицей.  
4. Внедрить retrieval слой для чата и формат ответа с provenance/citations.  
5. Написать полный Playwright e2e по сценарию заказчика.

### Этап B (укрепление качества)
1. Негативные integration tests: timeout источника, partial success, empty evidence, OCR error.  
2. Улучшить графовую панель: click-to-details с evidence snippets.  
3. Добавить кнопку «дозапустить источники» на странице отчёта/чата с частичным re-run.

---

## 7) Быстрые конкретные улучшения в коде (low effort / high impact)

1. В API `POST /requests` убрать `process_request(...)`; вместо этого только выставлять `status=created` и `PipelineEvent(created)`.  
2. В worker реализовать батч-claim запросов в статусе `created` и перевод в `processing` атомарно.  
3. В `source_runs` хранить `attempt`, `http_status`, `duration_ms`, `error_type`.  
4. В `evidence_items.meta_json` хранить `provenance` в фиксированном формате (`source`, `url_or_record_id`, `acquired_at`, `confidence`).  
5. В чат-ответах возвращать JSON-структуру: `answer`, `citations[]`, `insufficient_data: bool`, `suggested_reruns[]`.

---

## 8) Итоговая оценка

Текущий PR можно рассматривать как **хороший каркас/прототип**, но **не как завершённый MVP по ТЗ**.  
Для приёмки нужно закрыть P0-блок (worker orchestration, runtime adapters, полноценный e2e, explainable chat/report).
